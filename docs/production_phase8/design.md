# Phase 8 proposal and measurement boundary

Authorized 23 October 2026. Acceptance: measured performance change on the same fixed workload, preserved numerical/scientific results, unchanged planner/model/call sequence, full reliability/security regression and explicit scaling limits. vLLM, paid requests, cloud/GPU/Kubernetes and Phase 9 are excluded.

Phase 6 v2 already measured a one-worker queue bottleneck: ten mixed mock users had 38.88 s p95 queue wait, 44.35 s creation-to-terminal p95, 14 completions and six queue rejections. Production tool totals identify repeated community/sensitivity work as expensive. The API currently passes `--no-cache` to every run and resume, despite an existing validated deterministic graph-tool cache. Behavioral event, forecasting and research tools already bypass that cache and must continue to do so.

First profile the existing graph path without caching on the frozen synthetic 100-node input. Record CPU/function timings separately from uninstrumented timings. Then measure identical uncached, cold-cache and warm-cache jobs in an isolated mock-only state tree, preserving data/config hashes, seeds and scientific budgets. Record wall time, queue time, tool/cache flags, LLM calls/tokens, result fingerprints, process CPU/RSS and source/runtime identities. No performance threshold is inferred from a passing functional test.

Candidate smallest change: optionally reuse the existing deterministic cache from API jobs, scoped by authenticated owner, base config, implementation/dependency identity and execution mode. Preserve normal graph construction/checksum verification and tool validation/prerequisites before lookup. Never cache LLM replies or skip model calls. Bound retained entries/bytes and age; caching failure must not replace a scientific failure or stop otherwise executable work. Expose hits as explicit progress/telemetry, with a configuration switch for rollback. Default library/test settings remain uncached; enable the deployed service only after parity and controlled measurements pass.

Affected code if supported by profiling: a small operations cache-policy wrapper, Settings and worker argv construction, best-effort existing cache I/O guards, tests and measurement scripts. No analytical algorithm, scientific loop count/seed/precision, prompt, model, broker, budget grant, queue capacity or worker count change. Complexity is moderate because cache isolation, invalidation, storage failures and provenance require evidence. The same graph/spec can be reused only within the registered identity; failed/stale/oversized entries must be rejected and recomputed.

Retain the one-active/eight-waiting worker policy. A second API writer on one SQLite state tree remains unsupported and lease-rejected. Multiple independent hosts require coordinated durable admission, billing and artifact ownership; the current one-CPU workload does not justify Kubernetes. Do not call warm-cache speed a cold-algorithm or real-provider inference improvement.

Use the existing pinned Phase 7 image as the immutable before condition and a cumulative Phase 8 candidate as after. Preserve earlier benchmark protocols and all failed attempts. Source is already committed as 6f5631a; prior performance results have been inspected and are exploratory. New comparisons use the separately registered Phase 8 protocol below and do not rewrite Phase 6 results. Final runtime limits remain 1 CPU/2 GiB/128 PIDs and no new paid execution.
