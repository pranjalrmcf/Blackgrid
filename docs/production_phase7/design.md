# Phase 7 scope and acceptance

Authorized 23 October 2026. The active criterion is controlled failure recovery, tenant/input containment, current dependency/image vulnerability assessment and a consistent database-plus-artifact restore with unchanged scientific outputs. vLLM, paid calls, production fault injection, performance redesign and Phase 8 are excluded.

Existing controls already include durable bounded admission, unique idempotency, checkpoint/receipt verification, three-attempt local recovery, held uncertain paid reservations, one-worker leases, parent-death termination, network-denied workers, owner-bound artifacts, request/schema/size limits and sanitized logs. Reuse and execute these checks before adding protections.

The smallest new implementation is an offline state backup/restore module plus focused resilience/security checks and a reproducible isolated restore drill. Backup must refuse an active API or worker lease, retain every authoritative database and artifact, use SQLite's backup interface, hash the snapshot and publish a manifest only after completion. Restore must validate every file, reject traversal/symlinks/extra or missing files/corrupt databases, require a new destination and never overwrite an existing ledger. Backups remain private/local and are not ordinary report artifacts.

Drill only separate synthetic state: snapshot completed mock API jobs, restore into a new path/volume, verify every job/ledger field and saved aggregate result, then restart the restored application and verify ownership, idempotency, no duplicate processing and result parity. Preserve all failed attempts and timings. Test interrupted workers/API, provider timeout/rate-limit/malformed payloads without real network calls, actual SQLite write failure, partial output, admission/resource limits and adversarial API/tool inputs. Redis is not used and is inapplicable.

Run a current official vulnerability scanner against the exact local runtime image archive, with no Docker socket or credentials mounted and no private image upload. Record scanner/database/image identities, full coverage/skips and findings. Scan Python and OS packages; remediate supported security fixes narrowly with regression/parity evidence. If a critical vulnerability remains or scanning cannot complete, keep that release gate open rather than report a clean scan.

Affected areas: new operations backup module, its tests and isolated verification helper, incident/restore runbooks and acceptance evidence; existing boundary code or dependencies only when an executed check reveals a defect. Complexity is moderate, centered on consistent snapshots and failure classification. Keep the original image/state available. No live service restart while it has active jobs, no restoration over original spending records, no secret export or raw input redistribution. Local test target remains capped at 1 CPU/2 GiB/128 PIDs; no cloud service is needed.
