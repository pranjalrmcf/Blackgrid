# Phase 4 — asynchronous execution and data reliability

Status: completed for the bounded single-host API, 22 October 2026. Multi-host execution and independent legacy-ledger coordination remain outside this deployment boundary.

## Audit and implementation proposal

Phase 3 already launched a bounded trusted subprocess and persisted ownership, idempotency and full live-job reservations. Scientific runs already used SQLite/LangGraph checkpoints, operation receipts, cancellation flags and a classified LLM retry/reconciliation policy. Graph projection, Monte Carlo null tests, sensitivity analysis and provider calls are the long-running work. The API request body lived only in memory; another job was rejected while a worker ran; restart marked every queued/running job interrupted. Start/completion timestamps, safe automatic mock recovery and a waiting queue were missing. Terminal state could become visible before live billing settlement.

The smallest change is a single-process dispatcher backed by the existing API SQLite database. No Redis, Celery, additional service, distributed workers, new dependency or second scientific checkpoint store is needed at this workload. Affected files are the API job manager, worker containment wrapper, API readiness, command-line client, Docker test packaging, focused tests and documentation. Complexity is moderate: the important compatibility risks are crash recovery, uncertain billing and additive database migration. Verification uses synthetic inputs/fake providers, one container with 1 CPU/2 GiB/128 processes, and no paid calls. Dependency layers remain cached. No scientific method, prompt, model, LLM call sequence or frozen protocol is changed.

## Durable admission and lifecycle

One workflow executes at a time, with at most eight waiting jobs globally. A full queue returns HTTP 503 `queue_full` before accepting another request/reserving spend. An owner/idempotency replay is checked first and returns the same job even when full. The retained 5,000-job metadata limit still rejects new work instead of silently deleting history. SQLite `BEGIN IMMEDIATE` serializes request persistence and whole-job live reservations. The request, explicit paid authorization, base-config hash, creation time and initial state commit before dispatch. Questions remain private state; they are not added to logs or published evidence.

The dispatcher atomically claims a persisted request and records its first start, cumulative execution deadline and attempt count. Status adds `started_utc`, `completed_utc`, `attempts`, `result_ref` and `recovery_required`. Terminal states include completed, failed, cancelled, timed_out, abstained, paused and interrupted. Error codes describe the failure category without subprocess output, request contents or paths. Results remain owner-scoped and unavailable before completion. A completed manifest must have a completed investigation artifact; actual results remain minimized. For live jobs the terminal state, result reference, completion time and authoritative billing settle in the same database commit after the worker stops. Uncertain charges retain the whole job cap.

## Recovery and retries

Accepted waiting requests survive restart. Legacy incomplete rows without a request envelope become interrupted and require review. Newly interrupted/running **mock** work resumes through the existing `blackgrid resume` path, using the single run recorded in the scientific operation store, its saved config/source and existing checkpoint/receipt integrity checks. A final manifest is not required to locate an interrupted checkpoint. Ambiguous/missing checkpoint identity or partial artifacts without a usable run fail safely; a second scientific run is not started over those artifacts.

An exclusive per-job execution file lock is acquired inside the worker before importing the CLI. Recovery can force-unlock a scientific run only after acquiring this execution lock; a still-running old worker prevents that. On Linux the worker also binds SIGKILL to parent death and verifies that the expected parent still exists. The service-wide process lease prevents two API schedulers sharing the directory. Shutdown stops admission/dispatch, leaves waiting requests durable, drains the current child, then terminates/kills it within the documented grace. A still-running wrapper retains the service lease and reports incomplete shutdown instead of permitting a replacement writer.

Local mock launch failures, signal crashes and execution-lock contention retry at most three total attempts, with full-jitter exponential delay (0–2 s, then 0–4 s). The first-start wall-clock deadline is retained across retries/restarts. Bad config, invalid envelopes, partial artifacts, scientific failure/abstention, containment failure, cancellation and deadline exhaustion are not automatically retried. Final failed/timed-out rows form a retained terminal failure record; there is no automatic dead-letter requeue loop.

Running **live** jobs interrupted by application death are never automatically replayed: they become interrupted with `recovery_required=true` and keep the reservation. Waiting live jobs with no dispatch can run after restart using their previously saved explicit authorization and reservation. The existing workflow still owns provider retries, receipts and reconciliation; the job scheduler does not layer retries over paid calls. Exactly-once provider execution/billing cannot be guaranteed after an uncertain request. An operator must inspect existing receipts and resolve uncertain billing through the existing trusted workflow procedure before deliberate API-ledger reconciliation; no public grant-renewal/reconciliation endpoint is introduced.

Historical spend remains the reviewed host-ledger snapshot. All API clients share one transactional reservation ledger. Independent paid host CLI sessions must remain serialized with API use; this change does not make independent legacy ledgers a distributed accounting service.

## Cancellation, controls and failures

Waiting cancellation commits immediately, records completion and releases an unused live reservation without launching a child. Running cancellation sets the existing workflow cancellation flag, checked by the wrapper every 0.2 seconds and honored at scientific node boundaries. A current numerical tool/provider request may finish first. The existing workflow deadline is at most 900 seconds; the wrapper allows at most 930 seconds from first dispatch across attempts, then stops the child and records timed_out. Provider transport timeouts remain unchanged. Docker enforces 1 CPU, 2 GiB RAM, 128 processes, non-root execution and a read-only root filesystem; the worker retains its network syscall denial and fixed allowlisted CLI arguments.

SQLite connection/transaction failure stops the dispatcher and new admission, makes readiness fail with `job_scheduler_unavailable`, and leaves persisted requests/claims for inspection/restart. It never starts a second dispatcher or guesses that a reservation is free. Disk exhaustion and corruption require operator recovery; filesystem/SQLite state is not an external high-availability database. Worker stderr is suppressed so errors cannot disclose input data; stable categories and private checkpoints support diagnosis.

## Command-line progress

The question client now prints tool names, execution states and static analysis descriptions, for example `community_test | dispatched | Analysis: Community structure versus a degree-preserving null model`. Owner-scoped status exposes at most the latest 100 tool operation summaries from the authoritative workflow ledger. Completed tools missed between polls are printed on the next poll. The current tool is marked only while prepared/dispatched and the job is running. No tool arguments, graph identifiers, prompts, responses, node rankings or raw records are returned. Polling still occurs every two seconds; this is progress reporting, not streaming private reasoning.

## Retention and rollback

Retain completed artifacts and failed/partial checkpoints locally for at least 30 days, and retain job identities, idempotency records and all spend/reservation records for the lifetime of the project authorization. No automatic deletion is enabled: evidence and uncertain charges must not disappear on restart. At the 5,000-job limit or under disk pressure, stop admission and perform an operator-reviewed archival/cleanup with the service stopped. Archive private files securely, verify a restorable backup, retain the billing/idempotency database, and delete only explicitly reviewed terminal artifact folders after the retention period. Never delete active/waiting folders, pending reconciliation evidence, raw input files or the Docker state volume. The metadata cap bounds row count, not total disk bytes; volume capacity remains an operator responsibility.

Migration adds columns without dropping old rows. Before deployment, check for active jobs and take a consistent private SQLite backup within the state volume. Roll back the image only after stopping the service and reviewing queued/interrupted jobs. Preserve the newest ledger and charges; restoring an older database can erase spending and must not be used as a routine rollback. Phase 3 can read the additive schema but marks incomplete jobs interrupted; preserve the Phase 4 image/code for recovery. No automatic volume rollback or deletion is performed.

Acceptance criteria are met within the single-host boundary: concurrent submissions are bounded and serialized, worker crashes preserve and resume existing scientific records, duplicates share one job, cancellation follows documented limits, and exact offline numerical behavior is preserved. Memory/CPU limits are deployment controls rather than per-job containers. SQLite/disk/host loss still requires operator recovery; uncertain paid billing still requires review. These are explicit limits, not high-availability or exactly-once billing claims.
